# Traditional ML Evaluation Summary

This project keeps two complementary evaluation views:

1. Traditional machine learning metrics required by the course rubric.
2. System-level routing metrics used by the LLM gateway objective.

The traditional metrics are generated by:

```bash
python scripts/evaluate_traditional_ml.py
```

The script uses the same final real-time aligned experiment setup:

- train contexts: 2560 x 902
- validation contexts: 640 x 902
- prompt feature dimension: 896 Qwen activation dimensions
- system feature dimension: 6 serving-state dimensions

## 1. MLP Classifier Evaluation

The MLP Classifier is evaluated as a standard binary classifier.

Task:

```text
Predict whether the local model fails.
```

Positive class:

```text
local_failure = 1
```

The target is defined from the offline routing table:

```text
local_failure = score_local < 0.7
```

Metrics:

- accuracy
- precision
- recall
- F1
- train error = 1 - train accuracy
- validation error = 1 - validation accuracy
- confusion matrix
- precision-recall curve
- PR-AUC
- ROC-AUC
- learning curve across 10%, 25%, 50%, 75%, and 100% of training data

Checked-in report-facing files:

- `results/mlp_classifier_metrics.csv`
- `results/plots/mlp_classifier_confusion_matrix.png`
- `results/plots/mlp_classifier_precision_recall_curve.png`
- `results/plots/classifier_roc_auc_curve.png`

The learning-curve CSV and plot can be regenerated with
`scripts/evaluate_traditional_ml.py`, but they are not kept in the cleaned
GitHub `results/` folder.

Interpretation:

These metrics answer the question:

```text
How well does the MLP predict local model failure?
```

This is a normal supervised classification evaluation. It does not directly measure whether the route decision maximizes deployment utility.

## 2. Utility Router Evaluation

The Utility Prediction Router is evaluated as a binary route classifier against the oracle route.

Task:

```text
Choose local route or cloud route.
```

Reference label:

```text
oracle = argmax(true_utility_local, true_utility_cloud)
```

Positive class:

```text
cloud route = 1
```

Metrics:

- routing accuracy vs oracle
- precision_cloud
- recall_cloud
- F1_cloud
- confusion matrix vs oracle
- route error = 1 - routing accuracy
- precision-recall curve by SLA mode
- learning curve across 10%, 25%, 50%, 75%, and 100% of training data
- train and validation MSE for predicted utility_local and utility_cloud

Optional generated files:

`scripts/evaluate_traditional_ml.py` can regenerate strict routing
classification metrics, confusion matrices, and learning curves. These files
are useful for rubric completeness, but the cleaned GitHub `results/` folder
keeps the stronger utility-regression-specific evaluation figures instead.

Interpretation:

These metrics answer the question:

```text
How well does the Utility Router imitate the offline oracle routing decision?
```

The Utility Router is not trained as a classifier. It predicts two continuous values:

```text
Utility(local)
Utility(cloud)
```

The route decision is derived from whichever predicted utility is larger. For precision-recall analysis, the score is:

```text
predicted_utility_cloud - predicted_utility_local
```

## 3. Traditional ML Metrics vs System-Level Routing Metrics

Traditional ML metrics are useful because they are familiar and easy to compare:

- accuracy
- precision
- recall
- F1
- confusion matrix
- precision-recall curve
- ROC-AUC
- train/validation error
- learning curves

They evaluate whether a model matches a label.

For the MLP, the label is:

```text
local_failure
```

For the Utility Router, the label is:

```text
oracle route
```

System-level routing metrics evaluate whether the gateway behaves well as an LLM serving system:

- average utility
- average quality
- average cost
- average latency
- cloud route rate
- effective cloud cost

These metrics evaluate whether the route decision is useful operationally. For example, a router can have lower routing accuracy vs oracle but still achieve strong average utility if its mistakes are low-cost mistakes. Similarly, a model can classify local failures well but route to cloud too often or too rarely for a given budget and latency preference.

The final report should include both:

1. Traditional ML metrics to satisfy standard course evaluation expectations.
2. System-level metrics to show that the project solves the actual LLM routing gateway problem.

## 4. Undefined Metric Handling

All precision, recall, and F1 computations use:

```text
zero_division = 0
```

This prevents undefined metric errors when a model makes no positive predictions. In that case, precision or recall is reported as 0.
